# Implementation Status

Updated 2026-08-28. This file records verified behavior, not aspirational design.

## Working now

- Seeded-user sign-in with server-derived sessions.
- Personal and group Agent creation, lifecycle, persistent chat, and Runtime execution.
  Group Agent creation and management require the group's owner or an admin.
- Personal and group owner Workspaces with `shared/` and `projects/` boundaries;
  group tasks create one project directory shared by participating Agents.
- Independent Runtime state per Agent and conversation. Private conversations with
  the same group Agent do not reuse another human's model thread.
- Every Run receives an atomic `.launchpad/context.json` snapshot generated by the
  server. It contains the executing Agent identity, actual initiating human, exact
  conversation boundary, allowed conversation history, group roster/Agent/knowledge
  indexes, and workspace capabilities; it is evidence, not the authorization source.
- Every group Run also receives `.launchpad/group.json`, an explicit complete roster
  snapshot with exact human/Agent/resource counts. Prompts prohibit inferring group
  membership from who has spoken; the database remains the source of truth.
- Group-Agent direct messages may see the latest same-group chat history but
  never another member's private Agent conversation. Task steps see only committed
  events captured before that step starts.
- Project Agents write only in the current task directory. Owner `shared/` files
  are available through read-only Runtime operations, while publication requires
  a hash-bound human approval with overwrite ownership checks and audit records.
- Group creation; owner/admin member listing, add, and remove operations.
- Human group chat with no Agent required; manual and automatic Agent participation.
  When enabled, the visible system coordinator selects the useful Agents and their
  order for each response cycle instead of calling every Agent.
- A WeChat-style unified direct-message surface lists human contacts and every
  accessible non-coordinator Agent together. Human-to-human messages are persisted
  in a conversation visible only to its two participants; Agent chats keep their
  isolated Runtime threads.
- Multi-Agent task sessions with ordered turns, shared event history, replanning,
  timeout/failure visibility, retry, and stop controls.
- Group chats and tasks may enable one system-managed group coordinator. It emits validated
  `continue`, `complete`, or `await_human` decisions, selects only eligible participants,
  and can run multiple Agent rounds in automatic mode with a six-round safety cap.
- Task creation supports no-history, full-group-chat, or selected-message context
  import. Imports are same-group-only, copied as a fixed snapshot, and visibly
  summarized on the task page.
- Task pages show hash-bound result publication requests and let an authorized human
  approve or reject the exact proposed file.
- Task pages expose a nested source-file tree, bounded text previews, and ZIP download
  to current group members. Runtime metadata, Git internals, dependencies, and build
  output are excluded from the downloadable source bundle.
- Private and group resource policy enforcement in the backend and Runtime.
- Explicit private-resource grants, cross-user/cross-group denial, decision history,
  deterministic audit-detail redaction, automatic revocation of Run-scoped grants
  when a Run ends, and revocation of task-scoped grants when a task completes or
  stops. Run/task IDs supplied by browser clients cannot
  impersonate Runtime credentials, and task grants are bound to real participants.
- Optional Bouncer evidence contracts gate task completion on persisted Run-linked
  policy decisions. Missing actions fail the step and use the existing retry flow;
  vault command observations are stored without arguments or output.
- Private catalogs are absent from default Runtime context. The initiating human
  may approve metadata-only access to their own titles, kinds, and creation times
  for one Run; this does not grant content access. Exact references are blindly
  resolved and missing/inaccessible names fail identically.
- Unattached private-resource content requests first create metadata-only catalog
  approval even when the prompt names an exact title. After catalog approval, a
  separate read, disclosure, or forward approval may occur sequentially in the
  same logical Run. Attachments grant read only for the exact attached file.
- Access-request creation atomically moves the Run to `waiting_for_approval`.
  Fast decisions that arrive before the active Agent turn exits remain queued
  and resume exactly once. Approved continuations add a final-action evidence
  contract; if the resumed Agent skips the tool, the trusted control plane
  fulfills only that exact approved action and passes its result back to the Agent.
- External transfer capabilities require owner approval of one exact resource and
  registered recipient. An unattached own resource also requires a prior catalog
  approval in the same Run; an attached resource may enter forward approval
  directly. Free-form text, Agent output, and protected content cannot mint the
  capability; delivery is one-time and performed directly by the control plane.
- Initial chat entry scrolls to the newest message without pulling a user who has
  scrolled upward back to the bottom.
- The local POC can start without model credentials. Authenticated visitors can
  configure an OpenAI-compatible API key, model ID, and base URL in the Web UI;
  the key remains in server memory and is not persisted or returned.

## Partial

- Adding a group member currently means an owner/admin directly selects an existing
  platform user. There is no pending invitation, invitation link, or acceptance flow.
- Knowledge pages can create text resources, open resource details, grant a personal
  Agent access, and revoke that access. Browser-level acceptance is still pending;
  upload, edit, delete, and search controls are not implemented.
- Group tasks have real shared ordered state, but appear in a separate task tab rather
  than as collapsible child threads beneath specific group-chat messages.
- The coordinator uses a fixed platform prompt and six-round safety limit. Editing
  its policy or choosing a different maximum in the UI is not implemented.

## Not implemented yet

- Friend relationships and friend requests. Human-to-human direct messages work
  between seeded demo users without a friend graph.
- Selective/full/none import for new Agent direct-message threads; task import is
  implemented, while direct messages still use their existing private thread model.
- Group Agent mute/mention rules and per-user unread state.
- Task workspace checkpoints and rollback after failed Agent file changes.
- Static web preview and a disposable project runner.
- Registration, password recovery, production account administration, and external
  invitation delivery.
- Group rename/delete, role changes, and ownership transfer.

## Product boundary

Human-to-human messages use a separate `好友私信` surface and are not mixed into
`Agent 对话`, because the visibility owner and authorization policy are different.
The Track B submission does not require a social graph, so all seeded demo users
remain directly addressable until friend relationships are implemented.
